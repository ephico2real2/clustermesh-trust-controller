# ADR-010: Deliver realized source egress to the destination

**Status:** Proposed 2026-10-25, from source review and the live denial below. Security review pending. Tracks R7 ([NEXT_SESSION.md](../../handover/NEXT_SESSION.md), item 3).

Line references are to the Cilium fork at `6a00282808`.

## Problem, as measured

The destination ztunnel authorizes a caller only with the ALLOW rules the destination agent compiles. `policy.CompileZtunnelTCP` (`pkg/policy/ztunnel_l4.go:339`) admits a port only when the destination's realized ingress map permits the source identity and the source's realized egress map permits the destination identity. `effectivePolicyOwner.reconcile` (`pkg/ztunnel/xds/effective_policy.go:247`) passes as sources only the candidates of this agent (`:183`): captured workloads of this node. A source on another node or in another cluster matches no rule.

On 2026-10-25 at 21:55Z, with remote workloads projected on all four agents, a cross-cluster probe completed the HBONE handshake with `spiffe://cmtc-b.mesh.example/ns/cmtc-live-mtls/sa/mesh-client`. The destination ztunnel refused it with `no allow policies matched`. Cross-node probes are refused the same way.

The egress half cannot be enforced anywhere else. In-pod redirection sends the Pod's original connection to ztunnel inside the Pod's network namespace. The traffic that leaves the Pod is HBONE to port 15008, so the native egress map of the source never sees the original destination port. The source ztunnel's outbound check classifies destinations only.

## External evidence (checked 2026-10-25)

- **Upstream Cilium.** The [ztunnel encryption page](https://docs.cilium.io/en/latest/security/network/encryption-ztunnel/) states that "L4 policies won't work except for directly targeting the ztunnel HBONE port (15008)", and that "Cluster Mesh is not currently supported when ztunnel is enabled". Upstream has no source-egress mechanism to reuse.
- **Istio ambient.** The receiving ztunnel is the L4 enforcement point ([Istio L4 policy](https://istio.io/latest/docs/ambient/usage/l4-policy/)). CNI policy sees only port 15008 ([Istio and NetworkPolicy](https://istio.io/latest/docs/ambient/usage/networkpolicy/)). Calico restores the original port only with a modified ztunnel ([Tigera](https://docs.tigera.io/calico-enterprise/latest/compliance/istio/about-istio-ambient)).
- **Outbound is forwarding only.** On outbound, ztunnel "will determine where and how to forward the request"; it applies Authorization Policies on the inbound side ([Istio ambient data plane](https://istio.io/latest/docs/ambient/architecture/data-plane/)). No upstream component authorizes the source's egress.
- **Existing connections.** ztunnel re-checks every inbound connection when policies or workloads change, and closes those no longer allowed (fork `src/proxy/connection_manager.rs:478-488`). A narrowed plan therefore also ends established connections.
- **Addresses and identities across clusters.** "PodCIDR ranges in all clusters and all nodes must be non-conflicting and unique IP addresses", and every cluster must use the same `maxConnectedClusters` ([Cluster Mesh setup](https://docs.cilium.io/en/latest/network/clustermesh/setup/index.html)). The cluster ID occupies bits 16 to 23 of a security identity ([Security identities](https://docs.cilium.io/en/latest/internals/security-identities/)). So a source address resolves in the destination's ipcache to one Pod, and the receiver can fix the decode owner's `MaxConnectedClusters` to its own value.
- **Pod UID.** Kubernetes UIDs are distinct across the cluster's lifetime ([Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/)). The remote native IP record carries the Pod UID from the CiliumEndpoint (`clustermesh-apiserver/clustermesh/converters.go:270`), and the ipcache keeps it in `K8sMetadata.PodUID` (`pkg/ipcache/kvstore.go:430`). The cross-check therefore uses data the destination already holds.
- **etcd watches and leases.** A watch never repeats an event and never drops one within the history window, but watches are not linearizable ([etcd API guarantees](https://etcd.io/docs/v3.5/learning/api_guarantees/)). When a lease expires, its keys are deleted, and each deletion produces a delete event ([etcd API](https://etcd.io/docs/v3.5/learning/api/)). A reader that is disconnected sees no delete events at all, so the joiner's receiver-side expiry and epoch floors are still needed.
- **etcd request size.** The default maximum is 1.5 MiB, configurable with `--max-request-bytes` ([etcd system limits](https://etcd.io/docs/v3.5/dev-guide/limit/)).

## Decision

The source agent publishes each captured workload's realized egress map in its source membership record. The destination agent compiles remote sources from those records with the same compiler and the same rules as local ones.

1. **What is published.** `SourceMembershipEntry` (`pkg/ztunnel/membership/source_publisher.go:65`) gains an optional `egressPolicy` envelope with version, policy revision, selector revision, digest and wire bytes. The wire is `MarshalNative` (`pkg/policy/ztunnel_l4_wire.go:111`) of the **egress entries only** of the snapshot that local compilation uses (`Endpoint.SnapshotZtunnelReleaseCandidate`).
   - Egress lookups do not read ingress keys. The destination therefore gets exactly the input it needs, and no peer learns a source's ingress policy.
   - The envelope is bound to the entry's captured membership (epoch, ZDS generation, state).
   - While a regeneration is realizing a newer policy, the refresh waits for it at most 1 s in total (`sourcePolicyRealizationWait`). On the lab agents on 2026-10-25, 692 of 725 regenerations finished within 0.25 s (`cilium_endpoint_regeneration_time_stats_seconds`). Without the wait, a refresh that lands inside a regeneration would drop the source for a full 5 s refresh, and the destination ztunnel would close its established connections.
   - A policy still unrealized after the wait leaves the entry without an envelope. The workload stays a valid destination and is not a source until a later refresh. The publisher logs the change once, not on every refresh.

2. **Who reads it.**
   - **Same cluster, other nodes:** a new watch of this cluster's `…/ztunnel/membership/v1/agents/` prefix over a dedicated connection with the existing membership-writer credential. The writer role already has read access to the whole prefix (`pkg/kvstore/etcdinit/init.go:212`). The records go through the existing `SourceMembershipJoiner` lease logic in a mode with no IP-record join. That reuses its epoch and generation floors, replay refusal and receiver-side expiry (`source_join.go:321`, `:488`). This node's own record is ignored, because local candidates already cover it.
   - **Other clusters:** the existing direct-origin join carries the envelope (and the source endpoint ID) from the source entry into the joined `Workload`.

3. **How the destination uses it.** The policy owner adds remote sources to every plan, with each source subject built as follows:
   - **Cluster ID, name and trust domain.** For another cluster: its authenticated ID and name, and the trust domain the issuer profile approves for it. Sources of a peer are used only while its snapshot passes `projectRemoteSnapshot` (`remote_projection.go:62`), the same gate as remote destinations. For this cluster: the local values.
   - **Policy.** `DecodeNativeZtunnelL4` (`ztunnel_l4_wire.go:157`), with the expectation taken from the envelope and the owner fixed by the receiver: the authenticated source cluster ID and name, and the local `MaxConnectedClusters`. `validateZtunnelSubject` (`ztunnel_l4.go:217`) then refuses a snapshot bound to any other cluster.
   - **Native binding.** For every source address, the destination's own ipcache must map it to the subject's numeric identity and to the subject's Pod UID (`LookupByIP`, `GetK8sMetadata`). The destination's datapath uses that same view.

   A source that fails any check is left out, never approximated, and denied as before. Decoded snapshots are cached by digest.

4. **Change propagation.** The policy owner reconciles every second. It is also triggered when the same-cluster reader, the peer snapshot store or the trust view changes. The plan digest covers each source's content digest, so any source change republishes the destination's plan.

## Bounds and residual risk

- **Narrowed source egress** takes effect at other destinations after the source's next record refresh (5 s, `DefaultSourceRefreshInterval`), plus one reconcile (≤1 s) and the ztunnel ACK. On the same node, the existing `callerPlansCurrent` gate (`effective_policy.go:285`) still holds the release; across agents no such gate exists. A source agent that stops refreshing is removed when its 30 s lease expires.
- **Provenance is per cluster, not per node.** Every agent of a cluster holds the same writer credential, so one compromised agent can publish wider egress for workloads on other nodes. What it widens is only the *source's* own restriction, for traffic that must still come from that Pod's address with that Pod's SPIFFE identity, and the destination's ingress still applies. Per-node credentials remain open, as before.
- **Plan size.** A plan admits at most 64 sources (`maxZtunnelSources`). Beyond that, compilation fails and the destination denies every caller (fail closed). Sources are not prefiltered; raising the bound needs a measured plan size.
- **Record size.** Readers refuse a record over 1 MiB (`membership.MaxSourceMembershipRecordBytes`), which is below etcd's 1.5 MiB request limit. The writer enforces the same bound. The worst case is 8 workloads, each with every field at its maximum and an egress wire at `policy.MaxNativeZtunnelL4WireBytes` (82,048 bytes). It measures 888,391 bytes, a margin of 160,185 (`TestSourceMembershipRecordWorstCaseFitsReaderBound`). A record over the bound is withdrawn as `record_too_large` instead of being written.
- **Upgrade order.** The record decoder refuses unknown fields. A reader on an older build refuses a newer record and withdraws that peer's workloads (fail closed) until it is upgraded too.

## Alternatives rejected

- **Enforce egress at the source ztunnel.** That would need a new outbound authorization model in the fork, and two policy engines evaluating one decision.
- **Principal-only allow rules for remote callers.** That ignores Cilium source egress, which the compiler forbids by design (`ztunnel_l4.go`, `CompileZtunnelTCP`).
- **Copy egress into CiliumEndpoint status.** That means API churn on every regeneration, and a second, slower copy of what the membership lease already carries.

## Acceptance gates

- **Unit:** egress-only snapshot equivalence with the full snapshot for egress lookups. Envelope binding, size and decode refusals. Joiner without an IP record: floors, replay and expiry. The policy owner admits a remote source only with matching ipcache identity and Pod UID, an approved trust domain, a valid lease and a decodable snapshot; a narrowed egress republishes the plan without the port.
- **Live, both clusters:**
  - allowed: same-node, cross-node and cross-cluster, by Pod IP and Global Service, on ports 80, 8080 and 31337;
  - denied: the unregistered client and a source whose egress policy denies the destination;
  - recovery: agent restart, ztunnel restart, node reboot and drain.
