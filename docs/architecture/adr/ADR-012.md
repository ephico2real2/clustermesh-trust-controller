# ADR-012: The CMTC controller arbitrates the issuer approval; it follows cert-manager

**Status:** Proposed, 2026-10-27, for issue #34. **Implemented and unit-tested** on the branch
`feat/approval-follows-cert-manager`: the planner, the arbiter pass, the producer's follow mode, the node trust report,
the controller wiring, the chart (CRDs, configuration, RBAC, admission policies, node-agent mounts). The write
restriction of the node reports is **proven on Kubernetes v1.36.4** (a throwaway kind cluster, not the labs; see
[Node report write enforcement](#node-report-write-enforcement)). **Not deployed, not traffic-qualified.** See
[Implementation state](#implementation-state).

## Problem, as measured

- An approval lists, per cluster, the intermediate keys that may sign SPIRE's CA. ztunnel adds the pinned intermediate
  as the only trust anchor and requires pin -> exactly one SPIRE CA -> SVID (ztunnel fork `0e92198`,
  `src/tls/domain_anchors.rs:527`, `:543`, `:556`).
- cert-manager renews `<cluster>-spire-intermediate` with `rotationPolicy: Always` (`charts/cmtc/templates/trust.yaml:24`),
  so the renewal has a new key. SPIRE prepares its next CA at half of the current CA's life and activates it later
  (SPIRE v1.15.5, the labs' `spire-server` image, `pkg/server/ca/manager/manager.go:42`, `:46`). The cert-manager
  UpstreamAuthority requests each CA for `PreferredTtl` (`pkg/server/plugin/upstreamauthority/certmanager/api.go:50-51`)
  and deletes the CertificateRequest as soon as it is Ready (`api.go:66-108`, `certmanager.go:166-172`). SPIRE requests
  every CA for its `ca_ttl` (`server.conf`, parsed at `cmd/spire-server/cli/run/run.go:582-587`; 24 h when unset,
  `pkg/server/credtemplate/builder.go:30`, `:153-154`; passed to `MintX509CA` at `pkg/server/ca/manager/manager.go:987`),
  and cert-manager's own approver approves the request as asked (operator decision 2026-10-27T16:28Z: no
  approver-policy). So `ca_ttl` bounds every SPIRE CA, and no public object records which SPIRE CAs are live.
- An approval built on the administrator's host (`publish_issuers.py`) names one key per cluster. After a renewal, the
  first SPIRE CA under the new key is refused everywhere (`UnauthorizedIssuer`). The measured analogue:
  2026-10-27T10:33Z, every probe `curl 56` ([LOCAL_ISSUER_PROFILE.md, Rollout](../../../LOCAL_ISSUER_PROFILE.md)).
- An approval lasts at most 30 days (`internal/trustprofile/profile.go:317`), so it also needs a renewal without a
  host job.

## Decision

1. **The CMTC controller is the arbiter.** A leader-elected runnable inside the controller (not a Job) is the only
   writer of the approval (`internal/controller/issuer_approval.go`). It derives each cluster's current intermediate
   from public cert-manager objects, keeps the old and the new intermediate during the overlap, retires the old one
   after the last SPIRE CA under it can have expired and every node of every cluster trusts the successor, and renews
   the approval before it expires.
2. **The peer's public material is read from the peer's Kubernetes API** with a read-only ServiceAccount of the peer
   cluster (`cmtc-peer-reader`, `charts/cmtc/templates/peer-reader.yaml`) whose kubeconfig the administrator installs
   once as a Secret mounted into the controller (`controller.issuerApproval.clusters[].peerSecret`; the Istio and
   Linkerd remote-credential pattern). Each cluster's arbiter builds its own approval with every cluster's intermediate.
3. **The administrator approves only long-lived identities** in the Helm values (`controller.issuerApproval`): root
   SHA-256, each cluster's intermediate Certificate name and UID, its trust domain and its SPIRE CA policy. The
   instance material (certificate, SPKI) comes from public objects. No Secret is read through the API.
4. **The node agent reports each node's acceptance** in a `NodeTrustReport` named after its node
   (`internal/agent/trust_report.go`). Advance and retire wait for these reports from every node of every cluster. A
   missing or stale report blocks.
5. **Fail closed.** Anything unproven writes no approval. The last approval stays in force until it expires; that is
   a fail-closed property, not an uptime goal (operator, 2026-10-27T12:21Z). `rotationPolicy: Never` is not used: a
   kept key does not remove the 30-day renewal, and a key that never rotates is not the production practice.

### Internal reconcile, not a Job

| Concern | Internal leader-elected reconcile (chosen) | Owned Job |
|---|---|---|
| RBAC | The controller's ServiceAccount, named objects only | A second ServiceAccount with the same rights, plus the controller's rights to create Jobs and read their logs |
| Failure and retry | Every 15 s pass re-derives its state from the API; a failed pass retries on the next tick | Job backoff, then the controller must read the Job's outcome and decide |
| Observability | `IssuerApproval` status and conditions, metrics, one log line per pass | The same status, plus Job status and Pod logs to correlate |
| Restart | Stateless: the publication, the slots and the `IssuerApproval` record are the state | A Job can outlive its controller; ownership and leader handover must be reconciled |

The producer already runs this way (`internal/controller/issuer_profile.go`, `NeedLeaderElection`), so the arbiter
uses the same leader lease and handover timing (`issuer_approval.go:889`).

### Cross-cluster path

| Path | Evidence | Verdict |
|---|---|---|
| Peer Kubernetes API, read-only token of the peer (chosen) | The objects needed are public: Certificate, CertificateRequest `status.certificate`, ClusterIssuer, the SPIRE `server.conf` ConfigMap, Nodes, NodeTrustReports and the publication (`charts/cmtc/templates/peer-reader.yaml`: by name where the name is known, list without watch). | One mechanism for evidence and for the peer's node reports. The peer identity reads no Secret. |
| Cilium ClusterMesh / kvstoremesh etcd | The clustermesh-apiserver etcd users are created by the Cilium fork's `etcdinit` (`init.go:138-215`); no key path carries CMTC objects. | Needs a fork change and a new writer into Cilium's kvstore. Rejected. |
| SPIRE bundle endpoint / federation | Carries a trust bundle (roots), not the intermediate's Certificate identity or the policy bound. | Cannot prove the Certificate UID or the SPIRE CA bound. Rejected. |
| A published ConfigMap read by the peer | That is this path, read through the peer API. | Same as chosen. |
| Each cluster approves only its own intermediate | ztunnel needs every peer's intermediate pinned to accept its SVIDs (`domain_anchors.rs:527`). The peer's pin must still travel. | Moves the problem; rejected. |

The peer's material is authenticated, not merely received (`internal/controller/approval_evidence.go:78-167`): the
Certificate object must have the approved UID (`:83`), be a CA from the mesh root ClusterIssuer (`:93`); the
CertificateRequest of its current revision must be owned by it, annotated with that revision and issued by the same
issuer (`:107-114`), hold exactly one certificate (`:123-129`); the ClusterIssuer must sign from that Certificate's
Secret (`:136`); SPIRE's `server.conf` must name exactly that upstream (`:145`); the certificate must be signed by the
pinned mesh root, carry the cluster's common name and a key distinct from the root's
(`internal/trustprofile/intermediate.go:48-80`); its `notAfter` must equal the Certificate status (`:152`). A
contradiction is refused; a failed read is unavailable; neither writes anything.

The peer readers are direct API clients (`cmd/cmtc/main.go`, `issuerApprovalArbiter`; no informer cache) through the
same verified-HTTPS transport rules as the local API (`validateIssuerAPITransport`): a peer that is down never blocks
the controller's startup, and it shows as `EvidenceUnavailable` for that cluster.

## State machine

The arbiter writes immutable approval ConfigMaps into two fixed slots, `cmtc-issuer-approval-a` and `-b`, and records
its state in `IssuerApproval/cmtc` (namespaced, status only). One pass changes at most one slot.

| Phase | Meaning | Leaves when |
|---|---|---|
| `Pending` | No approval accepted yet | Every cluster's evidence is ready and every node reports: a `Bootstrap` generation is written |
| `Publishing` | A slot is written; the producer has not published it | The publication names the slot (promotion) |
| `Distributing` | Published; not every local node accepts it | Every local node's ztunnel checkpoint holds the generation and digest |
| `Overlapping` | Accepted; a cluster still has two intermediates | The old one retires |
| `Converged` | Accepted; one intermediate per cluster; nothing due | A renewal, a new key or a configuration change |
| `Blocked` | A change is due and a gate refuses it | The gate's evidence changes |

Gates, in order, for a new generation (`issuer_approval.go`, `Reconcile`): no slot is pending; a slot is free; the
plan validates exactly as the producer validates (`trustprofile.Validate`); the overlap invariant holds
(`trustprofile.CheckSuccession`: no key is dropped unless it expires, or its retirement bound passed and every node of
every cluster trusts its successor); every node of every cluster reports fresh and accepts its own cluster's live
generation. Conditions: `EvidenceReady`, `NodesConverged`, `Blocked` (reason names the gate or the planner's hold).

Retirement bound: `RetireAfter = first pass that read the successor + SPIRE ca_ttl + margin`
(`internal/trustprofile/plan.go`, `IssuerRecord.RetireAfter`; `spireCALifetime`, `approval_evidence.go`). cert-manager
signs from the Certificate's Secret, which holds the new key before the Certificate status names the new revision; no
SPIRE CA lives longer than the `ca_ttl` SPIRE requested it for; the margin covers cert-manager's cache lag and clock
skew. A `server.conf` that states `ca_ttl` other than once on a line of its own gives no bound, so no retirement, even
after an earlier pass read one (planner test `TestUnknownCATTLHoldsRetirementAfterAKnownBound`). The bound is the
largest `ca_ttl` seen while the key was current or superseded, so a `ca_ttl` lowered after the renewal does not shorten
it (planner test `TestRetirementBoundKeepsTheLargestPolicyDuration`). A `ca_ttl` larger before the arbiter first read
the key, or while `server.conf` could not be read, is not seen. Because SPIRE deletes its CertificateRequests, this bound is the
only evidence of "no live SPIRE CA under the old key" that public objects allow; the retirement additionally waits for
every node's ztunnel to hold the successor pin (the observed part). A lost record restarts the clock later, which only
delays a retirement.

At most two keys per cluster (`profile.go:358`). A third key waits (`OverlapFull`) until the first retires; the
successor of a key is the next key by `notBefore`, so the first key can retire on the mesh's trust in the second
(planner test `TestThirdKeyWaitsForARetirement`).

### Consumer acknowledgement

The Cilium agent and ztunnel export no issuer-profile metric of the accepted generation. What they record:

- The Cilium agent serves a publication only after it re-reads the named source and validates it
  (`pkg/ztunnel/issuerprofile/project.go:206`), and follows a successor source only with a strictly greater
  generation (`project.go:195`; `pkg/ztunnel/xds/issuer_profile.go:282-288`).
- ztunnel commits each publication to its checkpoint before it acknowledges it (`src/tls/profile_provider.rs:466`); the
  checkpoint's origin binds the installation, not the approval object (`src/tls/profile_checkpoint.rs:22-27`).

So a `Validated` checkpoint whose lease has not ended is the acceptance of both. The node agent reads it read-only
(`trust_report.go`, `ztunnelReport`) and reports the generation, the approval digest, the loaded roots and the trusted
intermediate keys.

## The six races

| # | Race | This change | Reason |
|---|---|---|---|
| 1 | The Cilium agent's Role named g5 while the publication named g6 | **Settled** | The two slot names are fixed and rendered into the readers' Role (`issuer-profile-rbac.yaml`), so the Role never changes with a generation. |
| 2 | The approval pinned the new intermediate while SPIRE's active CA was under the old one | **Settled** | The old and the new intermediate are both approved during the overlap; the old one retires only after the SPIRE CA bound and the mesh's trust in the successor (`TestIntermediateKeyRotationNeedsOverlap`, `TestIssuerApprovalArbiterLifecycle`). |
| 3 | SPIRE prepared its next CA from the old upstream before the switch | **Settled for trust** | A CA prepared under the old key is covered: the old key stays until `RetireAfter`, which bounds every CA it signed. Which chain SPIRE prepares stays SPIRE's behavior. |
| 4 | Root pins must be on every node before the consumers restart | **Partly; later** | A root change is refused (one root per approval, `HoldRootChanged`). The node agent adds approved roots to `pins.json` and never removes one, and reports the file's digest and roots. Whether the running Cilium agent loaded the new file is not observable; ztunnel's loaded roots are (`LoadedRootSHA256`). Issue to file: "Root rotation: make the Cilium agent's loaded pins observable and gate the restart order on it" (an agent-side report of the pins digest it loaded; the arbiter then refuses a root change until every node's agent and ztunnel report the new root). |
| 5 | A new ztunnel Pod has no workload certificates until its delegate entry exists | **Elsewhere** | The SPIRE registrar plans delegate entries (`internal/spireregistrar/plan.go:161-163`). The node agent has no SPIRE Admin access and reports `DelegateEntryObserved=Unknown`. |
| 6 | 2026-10-25: an approval pinned a CA that SPIRE then rotated | **Settled** | The approval pins the long-lived intermediate, not SPIRE's CA, and the ztunnel checkpoint no longer binds the approval object (`profile_checkpoint.rs:22-27`). |

## The node agent

- `NodeTrustReport` is cluster scoped and named after its node, written whole (no status subresource) by its node's
  agent every 30 s or on change (`trust_report.go`, `Report`).
- Least privilege: uid 0 with every capability dropped (`charts/cmtc/templates/node-agent.yaml`), because the
  consumers require a root-owned pins file and ztunnel's checkpoint is root-owned 0600. Host mounts: the pins
  directory (read-write only with `managePins`) and ztunnel's checkpoint directory, read-only. No Secret reads, no
  SPIRE socket. The read-only checkpoint mount is a deviation from "only the pins directory": without it the node agent
  cannot report what ztunnel accepts. RBAC: `get, create, update` on `nodetrustreports`, no `delete`.
- Pins file: the Cilium agent's decoder rules (`pkg/ztunnel/xds/issuer_profile.go:89-143`, ported in
  `trust_report.go`, `decodePins`); the old bytes kept as `pins.json.previous`; the new file renamed over the old one,
  no final newline, read back and verified. The file is never created and a root pin is never removed.

### Node report write enforcement

RBAC cannot limit `create` or `update` by the writer's node. The chart renders a `ValidatingAdmissionPolicy`
(`charts/cmtc/templates/node-trust-report.yaml`) that matches the node agent's ServiceAccount and requires
`request.userInfo.extra['authentication.kubernetes.io/node-name']` to be exactly `[<report name>]`. The API server
embeds that claim when it mints a Pod-bound ServiceAccount token from the Pod's `spec.nodeName` (Kubernetes
documentation, "Additional metadata in Pod bound tokens", stable since v1.32); the kubelet can request tokens only for
Pods it runs, so the claim names the node the agent runs on.

Proven on 2026-10-27 on a throwaway kind cluster with the labs' Kubernetes version (`kindest/node:v1.36.4`; the labs
run v1.36.4 on both clusters, `kubectl version` read-only), with the chart's rendered CRD, RBAC and policies and a Pod
under the `cmtc-node-agent` ServiceAccount:

| Request from the agent Pod on `cmtc-vap-control-plane` | Result |
|---|---|
| TokenReview of its token | `authentication.kubernetes.io/node-name: [cmtc-vap-control-plane]` |
| CREATE `NodeTrustReport/cmtc-vap-control-plane` | 201 |
| CREATE `NodeTrustReport/not-my-node` | 422, `ValidatingAdmissionPolicy 'cmtc-node-trust-report-owner' ... denied request: a CMTC node agent may write only the NodeTrustReport named after the node its token is bound to` |
| UPDATE its own report | 200 |
| UPDATE `other-node` (created by the administrator) | 422, same policy message |
| DELETE its own report | 403 (RBAC grants no delete) |
| `cmtc-controller` creates ConfigMap `cmtc-issuer-approval-a` / `cmtc-issuer-approval-g9` | created / denied by `cmtc-issuer-approval-slots` |
| `cmtc-controller` deletes `cmtc-issuer-approval-a` / `other-cm` | deleted / forbidden (RBAC names the slots) |

Record: [docs/evidence/approval-arbiter-20261027/vap-proof.log](../../evidence/approval-arbiter-20261027/vap-proof.log).
The same policy is to be verified on the labs during qualification (read-only until then).

## Lifecycle

- **Startup:** the arbiter needs no peer to start. A report counts as fresh only after this process saw its
  heartbeat move between two of its reads, the earlier one within the report age, so after a restart, or after
  passes that did not read a cluster, the first advance waits one heartbeat (30 s). The convergence and trust gates
  read every cluster on every pass that reaches them, so that wait is one heartbeat, not one per cluster.
- **Peer down:** that cluster's evidence is unavailable; its keys stay, and the expiry is not extended past the
  accepted approval's. A renewal waits (`RenewalWaitsForEvidence`) until the peer returns or the approval expires. A
  retirement waits: the peer's nodes cannot report trusting the successor.
- **Restart:** the state is the publication, the two slots and the `IssuerApproval` record. A slot written whose
  record update was lost is deleted on the next pass. A ConfigMap with a slot name that the arbiter did not write is
  never deleted (`ForeignSlot`).
- **Clock:** report freshness never compares the node's clock with the controller's. `RetireAfter` uses the
  controller's clock; the retirement margin covers skew.
- **Expiry chicken-and-egg:** when the publication's lease has ended, the gate needs only fresh reports, not
  acceptance, so an expired approval can be replaced.
- **Availability cost (by mandate):** one node without a fresh report blocks every advance of every cluster,
  including the renewal. The remedy is to repair the node or remove its Node object; there is no override.

## Scale

Local Nodes are read as metadata and NodeTrustReports from the manager's informers. Peer Nodes and reports are read
only when a gate asks, once per pass. At 5,000 nodes a report is about 1 KiB; a peer read is about 5 MiB, only while
a change is due. Not measured.
