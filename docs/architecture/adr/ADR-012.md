# ADR-012: The CMTC controller arbitrates the issuer approval; it follows cert-manager

**Status:** Draft, 2026-10-27, for issue #34. **Proposed.** Partly **implemented and unit-tested** on the local branch
`feat/approval-follows-cert-manager`: the planner, the arbiter pass, the producer's follow mode and the node trust

## Problem, as measured

- An approval lists, per cluster, the intermediate keys that may sign SPIRE's CA. ztunnel adds the pinned intermediate
  as the only trust anchor and requires pin -> exactly one SPIRE CA -> SVID (ztunnel fork `0e92198`,
  `src/tls/domain_anchors.rs:527`, `:543`, `:556`).
- cert-manager renews `<cluster>-spire-intermediate` with `rotationPolicy: Always`, so the renewal has a new key.
  SPIRE prepares its next CA at half of the current CA's life and activates it later (SPIRE
  `pkg/server/ca/manager/manager.go:42`, `:46`, `:1155`). The cert-manager UpstreamAuthority requests each CA for
  `PreferredTtl` (`pkg/server/plugin/upstreamauthority/certmanager/api.go:49`), so approver-policy's `maxDuration`
  bounds every SPIRE CA.
- Today an approval is built on the administrator's host (`publish_issuers.py`) and names one key per cluster. After
  a renewal, the first SPIRE CA under the new key is refused everywhere (`UnauthorizedIssuer`). The measured analogue:
  2026-10-27T10:33Z, every probe `curl 56` ([LOCAL_ISSUER_PROFILE.md, Rollout](../../../LOCAL_ISSUER_PROFILE.md)).
- An approval lasts at most 30 days (`internal/trustprofile/profile.go:316`), so it also needs a renewal without a
  host job.

## Decision

1. **The CMTC controller is the arbiter.** A leader-elected runnable inside the controller (not a Job) is the only
   writer of the approval. It derives each cluster's current intermediate from public cert-manager objects, keeps the
   old and the new intermediate during the overlap, retires the old one after the last SPIRE CA under it has expired,
   and renews the approval before it expires.
2. **The peer's public material is read from the peer's Kubernetes API**, with a read-only ServiceAccount token of the
   peer cluster that the administrator installs once (the Istio and Linkerd remote-secret pattern). Each cluster's
   arbiter builds its own approval with every cluster's intermediate.
3. **The administrator approves only long-lived identities** in the Helm values: root SHA-256, each cluster's
   intermediate Certificate name and UID, its trust domain and its SPIRE CA policy. The instance material (certificate,
   SPKI) comes from public objects. No Secret is read.
4. **The node agent reports each node's acceptance** in a `NodeTrustReport` named after its node. Advance and retire
   wait for these reports from every node of every cluster. A missing or stale report blocks.
5. **Fail closed.** Anything unproven writes no approval. The last approval stays in force until it expires; that is
   a fail-closed property, not an uptime goal (operator, 2026-10-27T12:21Z). `rotationPolicy: Never` is not used: a
   kept key does not remove the 30-day renewal, and a key that never rotates is not the production practice.

### Internal reconcile, not a Job

| Concern | Internal leader-elected reconcile (chosen) | Owned Job |
|---|---|---|
| RBAC | The controller's ServiceAccount, named objects only | A second ServiceAccount with the same rights, plus the controller's rights to create Jobs and read their logs |
| Failure and retry | Every 15 s pass re-derives its state from the API; a failed pass retries on the next tick | Job backoff, then the controller must read the Job's outcome and decide |
| Observability | `IssuerApproval` status and conditions, metrics, one log line per pass | The same status, plus Job status and Pod logs to correlate |
| Restart | Stateless: the publication, the slots and the `IssuerApproval` record are the state | A Job can outlive its controller; ownership and leader handover must be reconciled |

The producer already runs this way (`internal/controller/issuer_profile.go`, `NeedLeaderElection`), so the arbiter
uses the same leader lease and handover timing.

### Cross-cluster path

| Path | Evidence | Verdict |
|---|---|---|
| Peer Kubernetes API, read-only token of the peer (chosen) | Istio `istioctl create-remote-secret` and Linkerd multicluster `link` give each control plane a scoped credential for the peer API. The objects needed are public: Certificate, CertificateRequest `status.certificate`, ClusterIssuer, CertificateRequestPolicy, the SPIRE `server.conf` ConfigMap, Nodes, NodeTrustReports and the publication. | One mechanism for evidence and for the peer's node reports. The peer token is read-only and names objects; it never reads a Secret. |
| Cilium ClusterMesh / kvstoremesh etcd | The clustermesh-apiserver etcd users are created by the Cilium fork's `etcdinit` (`init.go:138-215`); no key path carries CMTC objects. | Needs a fork change and a new writer into Cilium's kvstore. Rejected. |
| SPIRE bundle endpoint / federation | Carries a trust bundle (roots), not the intermediate's Certificate identity or the policy bound. | Cannot prove the Certificate UID or the SPIRE CA bound. Rejected. |
| A published ConfigMap read by the peer | That is this path, read through the peer API. | Same as chosen. |
| Each cluster approves only its own intermediate | ztunnel needs every peer's intermediate pinned to accept its SVIDs (`domain_anchors.rs:527`). The peer's pin must still travel. | Moves the problem; rejected. |

The peer readers are direct API clients (no informer cache): a peer that is down never blocks the controller's
startup, and it shows as `EvidenceUnavailable` for that cluster.

## State machine

The arbiter writes immutable approval ConfigMaps into two fixed slots, `cmtc-issuer-approval-a` and `-b`, and records
its state in `IssuerApproval/cmtc` (namespaced, status only). One pass changes at most one slot.

| Phase | Meaning | Leaves when |
|---|---|---|
| `Pending` | No approval accepted yet | Every cluster's evidence is ready and every node reports: a `Bootstrap` generation is written |
| `Publishing` | A slot is written; the producer has not published it | The publication names the slot (promotion) |
| `Distributing` | Published; not every local node accepts it | Every local node's ztunnel checkpoint holds the generation and digest |
| `Overlapping` | Accepted; a cluster still has two intermediates | The old one retires |
| `Converged` | Accepted; one intermediate per cluster; nothing due | A renewal, a new key or a configuration change |
| `Blocked` | A change is due and a gate refuses it | The gate's evidence changes |

Gates, in order, for a new generation: a slot is free; the plan validates exactly as the producer validates
(`trustprofile.Validate`); the overlap invariant holds (`trustprofile.CheckSuccession`: no key is dropped unless it
expires, or its retirement bound passed and every node of every cluster trusts its successor); every node of every
cluster reports fresh and accepts its own cluster's live generation. Conditions: `EvidenceReady`, `NodesConverged`,
`Blocked` (reason names the gate or the planner's hold).

Retirement bound: `RetireAfter = first pass that read the successor + SPIRE CA maxDuration + margin`. cert-manager
signs no SPIRE CA under the old key after the successor is issued, and no SPIRE CA lives longer than `maxDuration`.
A lost record restarts the clock later, which only delays a retirement.

At most two keys per cluster (`profile.go:358`). A third key waits (`OverlapFull`) until the first retires; the
successor of a key is the next key by `notBefore`, so the first key can retire on the mesh's trust in the second
(planner test `TestThirdKeyWaitsForARetirement`).

### Consumer acknowledgement

The Cilium agent and ztunnel export no issuer-profile metric of the accepted generation. What they record:

- The Cilium agent serves a publication only after it re-reads the named source and validates it
  (`pkg/ztunnel/issuerprofile/project.go:206`), and follows a successor source only with a strictly greater
  generation (`project.go:195`; `pkg/ztunnel/xds/issuer_profile.go:282-288`).
- ztunnel commits each publication to its checkpoint before it acknowledges it (`src/tls/profile_provider.rs:466`); the
  checkpoint's origin binds the installation, not the approval object (`src/tls/profile_checkpoint.rs:22-27`).

So a `Validated` checkpoint whose lease has not ended is the acceptance of both. The node agent reads it read-only
and reports the generation, the approval digest, the loaded roots and the trusted intermediate keys.

## The six races

| # | Race | This change | Reason |
|---|---|---|---|
| 1 | The Cilium agent's Role named g5 while the publication named g6 | **Settled** | The two slot names are fixed, so the readers' Role never changes. |
| 2 | The approval pinned the new intermediate while SPIRE's active CA was under the old one | **Settled** | The old and the new intermediate are both approved during the overlap; the old one retires only after the SPIRE CA bound and the mesh's trust in the successor. |
| 3 | SPIRE prepared its next CA from the old upstream before the switch | **Settled for trust** | A CA prepared under the old key is covered: the old key stays until `RetireAfter`, which bounds every CA it signed. Which chain SPIRE prepares stays SPIRE's behavior. |
| 4 | Root pins must be on every node before the consumers restart | **Partly; later** | A root change is refused (one root per approval, `HoldRootChanged`). The node agent adds approved roots to `pins.json` and never removes one. Whether the running Cilium agent loaded the new file is not observable; issue to file. |
| 5 | A new ztunnel Pod has no workload certificates until its delegate entry exists | **Elsewhere** | The SPIRE registrar plans delegate entries (`internal/spireregistrar/plan.go:161-163`). The node agent has no SPIRE Admin access and reports `DelegateEntryObserved=Unknown`. |
| 6 | 2026-10-25: an approval pinned a CA that SPIRE then rotated | **Settled** | The approval pins the long-lived intermediate, not SPIRE's CA, and the ztunnel checkpoint no longer binds the approval object (`profile_checkpoint.rs:22-27`). |

## The node agent

- `NodeTrustReport` is cluster scoped and named after its node. Only that node's agent may write it: a
  ValidatingAdmissionPolicy compares `object.metadata.name` with
  `request.userInfo.extra['authentication.kubernetes.io/node-name']` of the node-bound ServiceAccount token
  (Kubernetes 1.36.4 on both labs). **Not built yet; not proven.**
- Least privilege: uid 0 with every capability dropped, because the consumers require a root-owned pins file and
  ztunnel's checkpoint is root-owned 0600. Host mounts: the pins directory (read-write only with `managePins`) and
  ztunnel's checkpoint directory, read-only. No Secret reads, no SPIRE socket. The read-only checkpoint mount is a
  deviation from "only the pins directory": without it the node agent cannot report what ztunnel accepts.
- Pins file: the Cilium agent's decoder rules; the old bytes kept as `pins.json.previous`; the new file renamed over
  the old one, no final newline, read back and verified. The file is never created and a root pin is never removed.

## Lifecycle

- **Startup:** the arbiter needs no peer to start. A report counts as fresh only after this process saw its
  heartbeat change, so after a restart the first advance waits one heartbeat (30 s).
- **Peer down:** that cluster's evidence is unavailable; its keys stay, and the expiry is not extended past the
  accepted approval's. A renewal waits (`RenewalWaitsForEvidence`) until the peer returns or the approval expires.
- **Restart:** the state is the publication, the two slots and the `IssuerApproval` record. A slot written whose
  record update was lost is deleted on the next pass.
- **Clock:** report freshness never compares the node's clock with the controller's. `RetireAfter` uses the
  controller's clock; the retirement margin covers skew.
- **Expiry chicken-and-egg:** when the publication's lease has ended, the gate needs only fresh reports, not
  acceptance, so an expired approval can be replaced.
- **Availability cost (by mandate):** one node without a fresh report blocks every advance of every cluster,
  including the renewal. The remedy is to repair the node or remove its Node object; there is no override.

## Scale

Local Nodes are read as metadata and NodeTrustReports from the manager's informers. Peer Nodes and reports are read
only when a gate asks, once per pass. At 5,000 nodes a report is about 1 KiB; a peer read is about 5 MiB, only while
a change is due. Not measured.
