# ADR-011: One 10-year mesh root minted by cert-manager in a control cluster, shared by every cluster

**Status:** Accepted by the operator on 2026-10-26. Applies first to ClusterMesh; SPIRE follows in a planned move.
Implementation: manifests prepared and validated by server-side dry run; nothing is applied yet. The cutover is in
the [runbook](../../evidence/clustermesh-pki-20261026/RUNBOOK.md).

## Problem, as measured

Every cluster of a mesh must trust the certificates of every other cluster. The labs got that trust from two separate
PKIs:

| PKI | Built by | Root | Per-cluster signer | Measured state, 2026-10-26 |
|---|---|---|---|---|
| ClusterMesh and ztunnel origin/membership | `scripts/lab/up.sh:51-117` | `CMTC disposable lab root`, 3 days, key deleted at `up.sh:117` | `<cluster> disposable intermediate`, 2 days | Intermediates expire 19:37:39Z (cmtc-a) and 19:37:43Z (cmtc-b). No key remains to renew them. |
| SPIRE | `scripts/lab/pki/pki.py`, `cmd/lab-identity-init` | `CMTC Lab Organization Root`, to 2031-10-24, key on the host | `<cluster> SPIRE cluster CA`, 1 year | In service. ztunnel pins the root certificate's SHA-256 `0c28af9e…4b7c` in every node's `pins.json`. |

`up.sh` was written for CI (`e36f853`, 2026-10-23; run by `.github/workflows/ci.yaml:99`). For clusters that live
minutes, a disposable root whose key is destroyed is the safe choice. The long-lived labs were built with the same
script on 2026-10-24, so they inherited lifetimes meant for a CI run.

## External evidence (checked 2026-10-26)

- **Cilium copies the CA, key included.** The Cluster Mesh setup guide shares one CA between clusters by copying the
  Kubernetes Secret that holds it (`cilium-ca` in `kube-system`) from one cluster to the other
  ([Setting up Cluster Mesh](https://docs.cilium.io/en/latest/network/clustermesh/setup/)). Decision 2 is that practice,
  applied to a cert-manager root.
- **Istio uses one root and one intermediate per cluster.** Each cluster's CA signs with an intermediate key and
  certificate signed by the root, so certificates of every cluster chain to one root
  ([Plug in CA Certificates](https://istio.io/v1.8/docs/tasks/security/cert-management/plugin-ca-cert/)). Decision 3
  is that layer.
- **cert-manager chains issuers this way.** A CA certificate issued by one issuer backs a CA ClusterIssuer that
  references the resulting Secret ([Linkerd cert-manager concepts](https://docs.buoyant.io/buoyant-enterprise-linkerd/latest/guides/cert-manager-concepts/)).
  Peers need the intermediate sent with the leaf ([cert-manager Certificate concepts](https://cert-manager.io/v1.0-docs/concepts/certificate/));
  the CA issuer returns `[leaf, intermediate]` in `tls.crt`, as the live leaves show today.
- **Copying onto an existing Secret.** A copy onto a cluster that already holds the Secret fails on immutable fields;
  the reported fix is `kubectl replace --force` ([Linux Foundation forum](https://forum.linuxfoundation.org/discussion/comment/42238)).
  Step 2 of the runbook copies onto a name that does not exist yet (checked on both clusters).

## Decision

1. **A control cluster owns the mesh root.** cert-manager in the control cluster mints one root out of the box: a
   `selfSigned` Issuer, then a Certificate with `isCA: true`, ECDSA P-256, `duration: 87600h` (10 years) and
   `rotationPolicy: Never`. This follows the operator's demo lab (`cilium-implementation-poc`,
   `clusters/eg/eg-root-ca.yaml`). In the lab, cmtc-a is the control cluster.
2. **The root Secret is copied to every cluster of the mesh,** so each cluster signs its own intermediate. Every
   cluster has a ClusterIssuer `cmtc-mesh-root` on that Secret.
3. **Each cluster's cert-manager issues its own intermediate per purpose** from `cmtc-mesh-root`. The ClusterMesh
   intermediate is the Certificate `cmtc-clustermesh-intermediate`: `isCA: true`, 1 year, renewed by cert-manager 30
   days before expiry. Its key is generated in its own cluster.
4. **The intermediate issues every leaf.** The existing ClusterIssuer `cmtc-lab-intermediate` points at the
   intermediate's Secret and keeps issuing and renewing all ClusterMesh and ztunnel origin/membership leaves.
5. **Trust is the root certificate.** `kube-system/cmtc-public-root` (`tls.caBundle`) carries it in every cluster. It
   is the only ClusterMesh trust input.
6. **CI keeps a disposable root.** `up.sh` in CI still creates and deletes its own root. Long-lived labs use the mesh
   root.

Manifests: [01-root-control-cmtc-a.yaml](../../evidence/clustermesh-pki-20261026/manifests/01-root-control-cmtc-a.yaml)
and [02-cluster-issuers.yaml](../../evidence/clustermesh-pki-20261026/manifests/02-cluster-issuers.yaml).

## Production shape

In production each cluster's cert-manager connects to the organization's external CA provider, such as Venafi or
Cloudflare. The operator reports (2026-10-26) that the provider distributes a signing CA, certificate and key, to
each cluster. It carries the rights of an intermediate signer (`CA:TRUE`, `keyCertSign`) and is most likely itself an
intermediate under the provider's root. The copied lab root stands in for that distributed signing CA: every cluster
signs under one shared chain with its own cert-manager, and no cluster depends on another to renew.

Four constraints carry over to the production design:

- **Path length.** If each cluster mints its own intermediate below the distributed CA (decision 3), that CA must allow
  one more CA level: no `pathLenConstraint`, or a value of at least 1. With `pathlen:0`, clusters can only issue
  leaves, and decision 3 does not apply. Check the distributed certificate's Basic Constraints.
- **Trust anchor.** The trust bundle (`cmtc-public-root`) should hold the provider's root, so that every cluster's
  distributed CA and its replacement verify without a bundle change. Pinning the distributed CA itself would make
  each provider rotation a trust rotation.

- **Key reuse.** cert-manager's documentation states that some issuers, the built-in Venafi issuer among them, may
  refuse to reuse a private key, so Certificates for them must use `rotationPolicy: Always`
  ([Certificate resource](https://cert-manager.io/v1.11-docs/usage/certificate)). The current ClusterMesh peer pins the
  server leaf key and relies on `rotationPolicy: Never`. With such a provider, a server key changes on every renewal,
  so the peer must pin something that survives renewal, such as a per-cluster CA.
- **What the provider can issue.** Whether a provider issues a per-cluster intermediate or only leaves decides
  whether the intermediate layer of decision 3 exists in production. This is to be checked per provider before the
  production design is fixed.

## Accepted risk

This risk applies to the lab only. The root key is in the etcd of every cluster of the mesh. Anyone who can read Secrets in `cert-manager` on any
cluster can mint certificates that every cluster accepts. This was raised during the design discussion: each cluster
could instead sign leaves with its own intermediate and receive only the root certificate. The operator chose the copy
so that each cluster is self-sufficient for its own intermediate. Mitigations: restrict `get` on Secrets in
`cert-manager` to cert-manager and the PKI owner, and audit reads of `cmtc-mesh-root-ca`.

## Alternatives rejected

- **Keep the disposable CI root on long-lived labs.** It fails by design within 2 days. The 2026-10-26 expiry is the
  measured result.
- **A root held off-cluster on the operator host** (the `pki.py` pattern). It keeps the key out of etcd, but it needs a
  host step for every intermediate. The operator wants every cluster to manage its own intermediate with cert-manager.
- **Leaves signed directly by the root,** as in the demo. A per-cluster intermediate lets one cluster's signer be
  replaced without touching the root, and limits each issuer's scope.

## Consequences

- **Leaf keys and pins.** The issuer switch alone changes no leaf key; each later issuance follows that Certificate's
  effective rotation policy. The ClusterMesh peer pins the server leaf
  key (`pkg/kvstore/remote_peer_identity.go:217-229`), so the server Certificate must keep its key across the reissue
  (`rotationPolicy: Never`, tested on cert-manager v1.21.1 on 2026-10-26: no reissue on the switch, key kept over 2
  renewals, control key changed over 2 renewals).
- **Root renewal.** With `rotationPolicy: Never`, a renewal of the root keeps its key and subject, so existing chains
  stay valid. The copies in the other clusters are not updated by cert-manager; they must be re-copied before the
  copied certificate expires.
- **Helm owns the bundle.** `cmtc-public-root` is rendered from `tls.caBundle.content`. The release values must carry
  the new bundle, or a `helm upgrade` that reuses the old values restores the old root.
- **SPIRE moves later.** SPIRE stays on `CMTC Lab Organization Root` until a planned rotation that pins the old and new
  root certificates together in `pins.json` and the issuer approval.
- **Pinning a CA instead of the leaf** is a separate decision.

## Acceptance gates

1. cmtc-a's `cmtc-mesh-root-ca` is Ready; its Secret is copied to cmtc-b; `cmtc-mesh-root` is Ready on both.
2. `cmtc-clustermesh-intermediate` is Ready on both clusters and chains to the mesh root.
3. Both clusters trust the mesh root in `cmtc-public-root`, and every ClusterMesh verifier has reloaded it.
4. All 7 Certificates of `cmtc-lab-intermediate` on both clusters are reissued and chain to the mesh root, and the
   server key SPKI is unchanged (cmtc-a `d1a0d97f…3214`, cmtc-b `0822f405…8199`).
5. The traffic join passes on all 6 paths of both clusters after each step, and after 19:37:43Z.
6. The disposable root is removed from the bundle before 2026-10-27T19:37Z, with the traffic join passing afterwards.
7. `up.sh` has a long-lived-lab mode that uses the mesh root, and CI still passes with the disposable one.
